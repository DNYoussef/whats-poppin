# Railway Supabase staging

User decision: self-host Supabase on Railway. This replaces the managed-project access prerequisite for this app. It authorizes provisioning the new staging resources, not a production data migration or application cutover.

Use a separate whats-poppin-supabase-staging Railway project in the existing workspace, with an environment named staging. This isolates the backend because live API documentation disagrees about whether service creation propagates across persistent environments. Do not clone existing variables or services. Preserve the existing What's Poppin project b5dc8a11-2f0a-4956-a8ca-0899a0364649. The CLI's current default link belongs to another project; use explicit resource IDs for API operations. Preserve production environment ca92fc09-72e1-4d21-a8e4-5b1480d58b73 and existing service ccc86351-94ec-4e97-80a8-78932ba45d46. Read back the intended project and environment before every deployment operation.

## Delivery and scope

Codex builds; Opus high independently audits. T2 standard deployment of known upstream components. Four build rounds and four inspection rounds, including plan inspection; no hidden retries after exhaustion. Existing isolated implementation branch continues. No local Docker. Build and validate containers on GitHub Ubuntu; Railway runs them remotely. Keep configuration and tests in this repository and record exact image digests and source revisions.

Deploy only the current core: Supabase Postgres, GoTrue Auth, PostgREST, an HTTPS API gateway, and private Mailpit for staging email confirmation. Storage, Realtime, Studio and Edge Functions are not connected app dependencies in this unit and are deferred to their owning features. This is a usable core Supabase backend, not a claim that every optional Supabase service is available.

Use upstream Supabase self-hosted/v0.8.0 database bootstrap role/JWT SQL with the documented Postgres 17.6.1.136, GoTrue v2.189.0 and PostgREST v14.12, pinned by registry digest. Use a pinned Nginx gateway image with declarative routing, API-key rejection; GoTrue/PostgREST perform actual JWT verification and role authorization. Never implement password handling or session signing in the gateway. Synthetic credentials are generated locally with cryptographic randomness and stored outside the checkout, then supplied through Railway's variables API without printing values. Keep the database on persistent storage and all services except the gateway private, with no public database proxy. No production credentials, users, provider keys or payment settings are copied.

Gateway contract: /auth/v1/* forwards to GoTrue and /rest/v1/* to PostgREST. Missing/invalid API keys fail closed except the email verification callback and OPTIONS. Bearer headers pass through unchanged; PostgREST uses PGRST_DB_ANON_ROLE for requests without a bearer token. Service-role requests must carry their own verified bearer token. Unsupported routes return 404. Do not log query tokens. CORS initially permits localhost development only. Auth requires email confirmation and delivers only into private Mailpit; live SMTP remains a production prerequisite. Signup/login/refresh/logout/confirmation are verified with synthetic users.

## Gate-first acceptance

1. Before deploying, implement a secret-free hosted container test with generated fixture credentials. Validate actual startup and gateway requests, not just YAML. Wrong API key and forged/expired JWT controls must fail; a valid signup-confirm-login control must succeed. Preserve bearer principal identity across simultaneous two-user calls.
2. Verify live Postgres includes PostGIS, vector and uuid-ossp, actual Supabase Auth roles/schema and PostgREST. Apply a small dedicated probe migration using Supabase's own migration history and pinned CLI with an explicit database connection; prove dry-run, apply, second no-op and a forward change. Use a restricted synthetic table for owner-only read/write and cross-user denial with successful owner controls. Do not weaken the existing disposable-stack or application privacy tests.
3. Deploy the reviewed configuration only to the new staging environment; observe each exact deployment as SUCCESS, then repeat health/Auth/RLS checks over its real API and a private database connection. Restart/redeploy the database and prove the synthetic data and migration history persist. Keep credentialed commands bounded and redacted. Read back production configuration to establish that it was preserved.
4. Record resources, gateway URL, image/source pins, migration versions, exact logs/markers and independent audit. Keep secrets out of source and reports. Do not claim production readiness, real outbound email, full application schema compatibility or complete H2/H3/H4 from a probe schema alone.
