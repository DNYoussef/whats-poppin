# Exact staging deployment procedure

Codex executes this procedure only after Opus high approves its snapshot and the exact source commit passes self-host, baseline, mobile and native GitHub checks. Runtime failures block deployment even if inspection is approved. Source branch is implement/whats-poppin-p00-20260907 in DNYoussef/whats-poppin.

1. Read back existing project b5dc8a11-2f0a-4956-a8ca-0899a0364649 and save its production service settings, domains and active deployment IDs outside the checkout. Preserve this project; every mutation below targets a different new project in workspace 8e743f4d-7fb0-4f26-a7de-e40fb02a6383. CLI calls use explicit IDs; never use the unrelated default link.
2. Create project whats-poppin-supabase-staging using Railway create-project with the workspace ID. Rename its sole default environment to staging through environmentRename. Read back the project/environment names and IDs and require no service instances. This deliberately avoids ambiguous multi-environment service-create semantics and does not copy production.
3. Create five empty services named sb-db, sb-auth, sb-rest, sb-gateway and sb-mail with create-service, specifying the new project/environment IDs on every call. Read back exactly those instances, with no deployments or domains. Create a volume for sb-db at /var/lib/postgresql/data with the same explicit IDs. No other volume or public TCP proxy is created.
4. Freeze the reviewed green SHA on a new deploy/supabase-staging-<sha-prefix> GitHub branch. Set DB and gateway root directories to /infra/supabase/db and /infra/supabase/gateway, Dockerfile path Dockerfile, restart ON_FAILURE with three retries and sleeping disabled. Gateway PORT is 8080 and healthcheck /healthz; Auth healthcheck /health with PORT 9999. REST PORT is 3000. Legacy root railway.toml must not be used by these isolated build roots; inspect each resolved build configuration and stop if it is applied.
5. Generate independent 32-byte hex values for POSTGRES_PASSWORD, AUTH_DB_PASSWORD, REST_DB_PASSWORD and JWT_SECRET outside the checkout. Generate HS256 anon/service_role keys with the latter secret, role/iss/iat/exp claims (one-year expiry recorded for rotation). Save state outside the checkout containing only the new IDs, credentials, service-name mapping and eventual API URL; never print credentials. Supply variables through Railway's variables API with skipDeploys=true. For each service use compose.yml's environment entries with required placeholders resolved, substituting private names sb-db/sb-auth/sb-rest/sb-mail. Use sb-db.railway.internal for database connections. Replace gateway upstream names with sb-auth.railway.internal and sb-rest.railway.internal. Auth SMTP host is sb-mail.railway.internal. Apply S3's placement matrix, especially distinct DB-role passwords and initially disabled signup. DB also gets DATABASE_URL for its own postgres database and PGHOST/PGPORT/PGUSER/PGDATABASE/PGPASSWORD so Railway's private CLI tunnel can identify it. The new project has no inherited application/provider/payment credentials.
6. Generate one Railway domain for sb-gateway at port 8080. Set Auth API_EXTERNAL_URL to that HTTPS URL before its first deployment. Connect DB/gateway to DNYoussef/whats-poppin at the frozen branch, and connect mail/auth/rest to the exact pinned images in compose.yml. Deploy DB and mail first, wait for their exact deployment IDs to reach SUCCESS, then Auth/REST/gateway. Capture exact IDs and source SHA/image references. Any FAILED/CRASHED/NEEDS_APPROVAL or timeout is unmet; inspect bounded redacted logs, fix within the declared round budget, and never call upload acceptance success.
7. Run python -B tests/self-host/run-railway.py <external-state-path> from the checkout. The runner checks project/environment/service identity and public-domain placement before mutations, opens only an SSH loopback database tunnel, temporarily enables signup with a new successful Auth deployment, then runs actual confirmation/identity/RLS/extension/migration checks. Probe migrations use isolated databases and external temporary workdirs. A DB restart must change pg_postmaster_start_time while retaining data, history and the encryption-key fingerprint. The finally path disables signup, removes each generated migration database and closes the tunnel. Explicit post-run checks require no probe tables/users and a denied new signup. Collect every success marker; never accept a partial run.
8. Read back all five exact deployment statuses, only one gateway domain, zero public TCP proxies, volume path, and source/image pins. Re-run the original project's production query and compare the saved canonical response. Keep the new staging backend for P01; do not switch the application variables, migrate production data, or claim app compatibility. Record measured extension versions alongside H1's PostGIS 3.3.7/vector 0.8.2/uuid-ossp 1.1; differences require H3b rehearsal and are not silently deemed equivalent. Record resources and evidence in SELF-HOST-GATES and HOSTED-GATES, leaving H3b/H4 and real SMTP open.

The private Mailpit inbox is a staging fixture, not production email delivery. Gateway /healthz proves only gateway readiness; actual Auth/PostgREST/SQL probes decide backend readiness. No project-wide IaC apply is part of this procedure. P10 imports the entire actual topology before any future apply.
